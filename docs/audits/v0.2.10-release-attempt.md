# v0.2.10 coordinated release attempt

The first [coordinated stable run](https://github.com/ropbet-radbyt/sorotte/actions/runs/34086010203)
used annotated tag `v0.2.10` at protected-main commit
`9f631f053ab431f56079e6ae4575fa5b0a9dc64a`. It finished unsuccessfully on its
original attempt on 7 September 2026. No stable release assets or server image
were published. The tag remains unchanged; the corrected candidate is v0.2.11.

## Passing evidence and limits

The original stable lifecycle completed all 75 required transitions on Windows
and Linux, including actual missing-file recovery and replacement of the owned
player. The Windows workspace and all server behavior obligations passed. The
GUI archive was built from the qualified Windows binaries and passed its archive
and runtime checks. Its elevated updater check proved launch and refusal before
mutation, not installation or rollback.

The isolated Windows runner automatically unregistered and its owned guest,
processes and registration tokens were independently confirmed absent. All
original logs, official artifacts and local reproductions are retained under
`target/verification/release-v0.2.10/` in the release worktree. A normal cancellation
request arrived after the workflow had already failed and received HTTP 409;
no cancellation or retry changed the original attempt.

These passing boundaries do not make the failed run a complete release. They
also do not establish a speed improvement. The v0.2.11 candidate requires fresh
source-bound hosted and release qualification after the repairs are committed.

## v0.2.11 main qualification follow-up

PR #46 merged the repairs at `d9df5f01238b79add183a94f1a4b62d1843dfa0b`.
Its original PR qualification passed. The fresh main
[Rust run](https://github.com/ropbet-radbyt/sorotte/actions/runs/34092791898)
then failed in Windows apparatus preflight: the real receipt concurrency canary
timed out after 25 seconds waiting for its 600 durable writes. Its reader's
20-second clock also included the readiness handshake, and the fixture discarded
both workers' output during timeout cleanup. The original evidence establishes
a timeout; it does not establish receipt corruption or the hosted slowdown's cause.

The unchanged canary passed locally. A controlled experiment added an eight-second
setup delay and 30 milliseconds after each actual publication. It reproduced the
same timeout while every observed receipt remained complete. A prototype that
separated readiness and work budgets completed the identical delayed workload:
600 writes, 18,133 valid reads, 600 observed versions, final sequence 600 and no
pending files. These deliberate delays demonstrate a fixture weakness; they are
not a reconstruction of the hosted machine's performance.

The repair gives each worker a separate 20-second readiness budget and a
60-second work budget, supervised together by one 90-second outer deadline and
at most ten seconds of owned-process cleanup. Either worker's failure is observed
without waiting for its peer. File-backed stdout/stderr and periodic progress
snapshots are included in failure diagnostics. The real publisher and reader,
600 writes, minimum read/version counts, final sequence and pending-file assertions
are preserved. The interruption and watchdog canaries keep their existing limits.
Four fast, cross-platform process regressions cover slower valid progress, an
early reader failure, both workers hanging and completion after an expired deadline.

The enclosing apparatus command allows 420 seconds, with a ten-minute hosted job
limit so bounded failure cleanup and artifact upload have room to finish. These
are maximum budgets; the repair introduces no deliberate delay in the healthy
600-write canary. The controlled long-delay experiment remains separate from the
ordinary suite.

The failed main attempt and both worker diagnostics from the experiments are
retained under `target/verification/release-v0.2.11/main-d9df5f0/`. Fuzzing,
package/dependency checks and isolated native qualification passed independently;
the native runner and guest were removed automatically. GUI-dev correctly stopped
at the failed Rust readiness check before minting an App token or publishing.
Those component passes cannot qualify a subsequent repaired source commit.

## Persistence fixture isolation follow-up

PR #47's original [Windows all-feature run](https://github.com/ropbet-radbyt/sorotte/actions/runs/34097391733/job/101668631870)
reported the secret-baseline persistence test's assertions as successful, then
the test process aborted with status `0xc0000409`. Its configured diagnostic
retry passed. The required gate correctly rejected that inconsistent result.
The retained JUnit and direct job log contain no native exception parameter,
dump or stack, so they do not establish the cause of the abort.

Investigation independently found that this settings fixture could start real
public-server HTTP work. Its `completed = true` shortcut left the hydration
context unset; reconciliation with the saved language reset that flag and
started a worker. A new assertion reproduced this defect deterministically:
one worker was started where the persistence fixture required zero. A
process-local response override prevented external HTTP during this diagnostic.

The fixture now supplies an explicit empty cached server list, using the existing
startup contract, and asserts both zero hydration attempts and no retained worker.
All four replace/clear and resync/patch combinations keep their original cancel,
saved-secret and disk/saved/draft persistence assertions. The same regression
passes with the fixture repair. Production startup behavior and fail-on-flaky
policy are unchanged. Twenty executions of the original binary against an owned,
delayed local HTTP fixture made 80 requests, with replies still pending at process
exit; twenty executions of the corrected binary made zero requests. Both groups
passed and cleaned up, without reproducing the native abort. Removing this
unrelated network dependency does not, by
itself, diagnose the original native abort or establish a suite-wide speed gain.

## Scheduled check collision follow-up

After PR #47 merged at `c10d6a62d8b0ccf449b35472f4c6fc2e588f8ba9`, the original
[GUI preview run](https://github.com/ropbet-radbyt/sorotte/actions/runs/34109070258)
stopped before App-token creation with
`verification-required: expected one latest check, found 2`. The ordinary
[main-push Rust run](https://github.com/ropbet-radbyt/sorotte/actions/runs/34109069841)
passed. A concurrent
[scheduled Rust run](https://github.com/ropbet-radbyt/sorotte/actions/runs/34109148973)
created skipped `verification-required` and `merge-required` checks with the same
names and source. The API's latest-check inventory retained both workflow runs.
Job conditions prevented execution but did not prevent those check records.
No preview lifecycle, archive build or publication ran.

The correction reserves required check names for push and PR events and gives
scheduled or manually dispatched aggregates distinct names. The same naming
boundary applies to mutation, fuzz, dependency and package workflows. Their
concurrency groups also include the event, preserving same-event supersession
while separating assurance runs from main-push qualification. Job IDs, dependency
edges, commands, conditions, cancellation rules and the strict release authorizer
remain unchanged. The native required consumer already accepts only push and PR
events and retains its existing name.

The original failure, both check records and their direct workflow/job provenance
are retained under `target/verification/release-v0.2.11/gui-dev-c10d6a6/`. A retry
cannot remove the conflicting records; the corrected source needs fresh PR and
main qualification before the v0.2.11 tag is created.

## Linux process observation follow-up

After PR #48 merged at `f8b907d7fdb35508274af68d2d2a104f7ca901cf`, the original
[framed-session fuzz job](https://github.com/ropbet-radbyt/sorotte/actions/runs/34119719519/job/101734797102)
failed in its policy tests before building or running that fuzz target. The
timeout-cleanup test checked that `/proc/<child>/stat` existed, then its read
raised `ProcessLookupError: [Errno 3] No such process`. The child disappeared
during the observation. This was a test-side race, not a fuzz crash or evidence
that a child remained alive. The subsequent artifact upload failed because the
campaign had not created its output directory. The identical PR policy test had
passed; that earlier result does not qualify this failed main attempt.

The assertion now reads the process state once and accepts only the two errors
that mean the process disappeared: `FileNotFoundError` and `ProcessLookupError`.
It still rejects a live process and propagates permission and I/O errors. The
mutation process tests contained the same observation pattern; their correction
also preserves the additional signal-zero check when the process entry is gone.
Deterministic regressions exercise both disappearance errors and retain live,
zombie, unreadable and surviving-PID controls. Production process termination,
timeouts and the real parent/child cleanup experiments are unchanged.

Original logs and partial workflow evidence remain under
`target/verification/release-v0.2.11/main-f8b907d/`. Superseded main campaigns and
the pre-App GUI readiness wait were cancelled after preserving their evidence.
Neither those cancellations nor successful individual components qualify this
source for a release. The v0.2.11 tag remains pending fresh qualification.

## Default-workspace validation before the next merge

All original PR #49 checks passed at
`07c6d73e45a9ac322482faace846538a0da69944`, including the Linux and Windows
all-feature nextest runs. Additional local execution of the release command,
`cargo test --locked --workspace`, passed on Windows but exposed two issues on
Linux before that PR was merged. Both failed full-workspace attempts are retained
under `target/verification/release-v0.2.11/pr-07c6d73/premerge-default-linux/`;
neither produced a successful workspace qualification receipt.

The unmanaged-player ownership fixture used `current_exe()` as its requested
player. A build-cache ancestor containing `mpv` made the existing Python-compatible
classifier select managed mpv, invalidating the fixture's unmanaged-path
assumption. The identical binary failed from that path and passed from a neutral
path with the same environment. The fixture now copies its executable to an
explicitly unmanaged `mpvnet` filename under a deliberately `mpv`-containing parent
and checks that classification before launch. Its actual spawn, child-survival,
release and completion assertions remain intact. Owned executable cleanup waits
for Windows to finish releasing the child's mapped image; the production player
classifier is unchanged.

The full Linux run using a neutral target then failed
`shared_readers_overlap_while_excluding_a_writer` with `stored settings are busy`.
Its unique temporary lock file was on the Linux filesystem. The failing outer
unwrap does not distinguish initial reader acquisition from a propagated nested
reader error, and an unchanged isolated execution passed. The original scheduling
was not traced.

A controlled reproduction imported the unchanged production transaction module
and kept a forked child alive with an inherited, close-on-exec file description.
Ending a writer's scope still blocked readers; ending a reader's scope still
blocked writers. Both recovered after the child exited. This establishes a lock
lifetime defect independently of the untraced failure: closing the parent's file
alone does not release an inherited open-file-description lock. The behavior
matches the documented [Linux flock semantics](https://man7.org/linux/man-pages/man2/flock.2.html).

Reader and writer acquisition now create an owning guard immediately after
successful locking. It explicitly unlocks before closing the file, including
writer destination-validation errors and both reader paths. The same controlled
reproduction passes with the child still alive. Seven deterministic regressions
retain a duplicate descriptor through success, validation failure, callback error
and panic; they also preserve exclusion by active owners and independent nested
readers. All seven fail against the original transaction implementation and pass
with the repair on Windows and Linux. Existing zero-timeout assertions, production
deadlines and file-opening protections are unchanged.

The new regressions execute under the existing PR checks. The complete
uninstrumented default-feature workspace, larger nonpublishing release lifecycle
and qualified-binary handoff are still distinct from the enforced PR composition.
Moving those combinations into required PR jobs remains a testing-process
follow-up. Actual merged-source, tag, authorization and published-byte checks must
continue to verify their final state. Earlier successful checks do not qualify a
subsequent source revision.
