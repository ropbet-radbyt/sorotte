# Playback regressions for 0.2.14

The reported environment was the latest tagged server and clients, local files
for the playlist failure, and direct Plex playback for delayed resume of an
already loaded video. Seek was not tested in the reported session.

## Reproduced failures

The baseline production source is `8f1005cd327ba39be459bed6d543d73420087fa1`,
the main merge of 0.2.13. New regressions failed against that source before
the fixes were applied.

| Failure | Cause and correction | Evidence |
| --- | --- | --- |
| Adding a second local item leaves the GUI and player on the first item after selecting the second. Later edits remain stuck. | The GUI retained a second optimistic playlist, cleared only by an exact files-and-index match. An append acknowledgement arriving after a newer selection could never match it. The client session already reconciles canonical replies with pending edits; the GUI now reads that single projection. | `current_server_pending_append_cannot_mask_newer_selection` failed with GUI index 0 and session index 1. `real_mpv_current_server_local_file_append_select_then_edit` also failed with mpv still on the first WAV. Both pass with the fix, including a subsequent delete. A separate current-server sequence covers append, selection, deletion, undo and queue-and-select. |
| Participants appear as Loading with fresh reports while the video plays. | The coordinator's `Starting` diagnostic also describes its recovery stability wait. Repeated physical position samples can retain that diagnostic during advancing playback. The playlist's canonical room intent, the session's pending edits, local source
resolution and the loaded player file remain distinct responsibilities. The GUI
does not own another playlist revision. Participant status remains advisory and
does not change readiness or room control.

## Plex reproduction boundaries

Clean-profile local HTTP/Plex-identity fixtures and a read-only direct stream
from the configured Plex server resumed within the one-second test budget.
The investigation included current readiness
protocol support, a controlled room, coordinated start, GUI and remote controls,
a half-second position difference, and 30-second pauses with release-pinned mpv.

Two actual GUI runtime owners with separate mpv processes also resolved the same
direct Plex stream through the normal source-resolution worker. Both clients
played before each pause. Alternating the initiating client across four resumes
produced eight physical resume measurements between 75 and 157 milliseconds.
The same test with the installed profile reproduced the overflow failure above.
This test includes both clients' actual readiness; no participant is made
artificially Playable. It is retained as the explicitly provisioned manual test
`real_mpv_two_plex_clients_resume_loaded_stream`.

A disposable Windows Sandbox also rendered the direct Plex video with `gpu-next`
while a simulated watch-sync request stayed pending. Its three resumes took
62, 86 and 87 milliseconds. Watch-history writes were disabled. The Sandbox was
stopped and its temporary private input removed. These are local reproductions,
not hosted release qualification.

A second Sandbox run rendered both actual Plex players with the copied profile
and both overflow fixes. All four alternating pause/resume cycles passed, with
eight resume measurements of 43–141 ms. That guest was also stopped and its
private input removed. The isolated test disables profile resume-file writes
and Plex watch-history synchronization.

A further rendered run explicitly selected and verified Windows WASAPI audio
output for both players, with the copied profile and muted output. Its eight
resume measurements were 38–190 ms. The audio logs were redacted, the Sandbox
stopped and the private input removed. This checks the Windows audio path in
addition to the earlier null-audio runs.

The observed 5–30 second delay from the original session has not been reproduced
with that exact timing. The configured-profile reproduction instead exposed a
persistent loss of synchronization in the same player observation/control path.
The tests prove recovery from those two defects and bounded resume for the
tested streams and profiles; they do not establish a latency bound for every
Plex server, network or transcoding configuration. The reported case was direct
playback. Seek remains outside the reported reproduction.

## Regression execution

The new current-server tests run against `ServerRuntime`, the GUI runtime owner
and real mpv. Native qualification now requires all four opt-in real-mpv cases;
a missing, skipped or failed case fails that stage. Their default inputs are
local fixtures, with no Plex credentials or external media required.

The first hosted Windows candidate exposed a fixture error before the playlist
sequence began: its temporary path used an 8.3 username, while the opened path
had the expanded username. Reproducing with an owned short-path temporary root
failed at the same three-second wait. The fixture now compares canonical file
identity, preserving the original path as the application input. The same
reproduction passes in 0.2 seconds; the timeout and playlist assertions remain.

Local client-core and GUI suites passed, including 1,185 GUI tests and all seven
new hermetic current-server regressions. All 450 player unit tests pass after
the overflow fixes. Static preflight, all-feature/all-target workspace Clippy,
the default full workspace lane and all 14 GUI semantic scenarios passed on the
initial playlist/status changes. The final source must complete full workspace,
hosted, packaged and native release qualification under
[the release contract](../RELEASE_QUALIFICATION.md).
